# 요구사항 정의서 — 항공 여행 일정 플래너

SSAFY AI 코어 프로젝트 3회차 · Agent 기반 도메인 플래너 서비스 · 작성 김현수 (SSAFY 16기)

> 명세서 6장 산출물 1) 요구사항 정의서입니다. 필수·심화 요구사항 표(F3001 ~), 선택한 도메인과 조건 충족 근거, 기획 검증 결과(외부 API 호출 확인, Tool 출력 구조 대조, 설계 시험과 그에 따른 설계 변경)를 담았습니다.
> 기획 당시의 결정 과정은 [PLAN.md](PLAN.md)(2일차 기준), 최신 설계는 [AGENT.md](AGENT.md) · [TOOLS.md](TOOLS.md) · [API.md](API.md), 검증 결과는 [VERIFICATION.md](VERIFICATION.md)에 있습니다.

## 1. 서비스 개요

"센다이 가는 가장 빠른 편", "인천공항에 9시 도착하는데 탈 수 있는 오사카행"처럼 말로 물으면, 에이전트가 요청을 분석해 공공데이터(인천국제공항공사·한국공항공사) 도구를 골라 부르고, **공항 도착 시각·준비 시간 같은 사용자의 제약과 비교**해 탈 수 있는 항공편을 추천합니다. 맞는 편이 없으면 조건을 넓혀 다시 계획하고(최대 3회), 추천받은 편은 '내 계획'으로 저장·조회·수정·삭제합니다. 메인 Agent 의 실행 과정은 로깅 Agent 가 이벤트로 받아 세션 단위로 저장합니다.

## 2. 도메인 선택 조건과 근거 (명세 1.2 · 2.1)

### 2.1 Tool 로 래핑한 외부 API (서로 다른 정보 3종 이상)

| # | 제공 | 서비스 | 주는 정보 | 쓰는 Tool | 개발계정 하루 한도 |
|---|---|---|---|---|---|
| 1 | 인천국제공항공사 | 여객기 운항 현황 상세 조회 (StatusOfPassengerFlightsDeOdp) | 인천 출발·도착 편, 예정·변경 시각, 터미널, 탑승구, 상태 | search_departures · search_arrivals · search_flight · get_flight_detail | 500 |
| 2 | 한국공항공사 | 실시간 운항 정보 (flight-status: depart, arrival, info) | 김포 등 14개 공항 출발·도착 편, 당일 탑승구(info) | search_departures · search_arrivals · search_flight · get_flight_detail · get_hourly_traffic(대체) | 5,000 |
| 3 | 한국공항공사 | 공항 혼잡도 (airport-congestion v1·v2) | 김포·제주·김해·청주·대구 국내선 구간별 혼잡 단계(지금) | get_airport_congestion | 5,000 |
| 4 | 인천국제공항공사 | 승객 예고 (passgrAnncmt) | 인천 T1·T2 출국장·입국장 시간대별 예상 인원(오늘·내일) | get_incheon_passenger_forecast | 1,000 |
| 5 | 인천국제공항공사 | 상업시설 정보 (StatusOfFacility) | 인천 면세점·식당·약국 등 이름·품목·위치·운영 시간 | get_incheon_facilities | 1,000 |
| 6 | 한국공항공사 | 전국공항 임대계약 정보 (airport-lease-contract) | 14개 공항 매장 업체·업종·위치 | get_commercial_facilities | 5,000 |
| 7 | 한국공항공사 | 전국공항 시간대별 탑승승객 수 (daily-expect-passenger) | 시간대별 이용 흐름 (안 되면 2번으로 편수를 셈) | get_hourly_traffic | 5,000 |

- 출처: 공공데이터포털(data.go.kr). 각 데이터의 이용허락범위와 포털 이용약관을 따르고 출처를 화면 하단·README·답변의 '근거 자료'에 표시합니다 (NF3007).
- 한도 보호: 같은 요청은 5분(시설·매장은 6시간) 동안 재사용합니다. 승객 예고는 '예상 인원' 표현만 씁니다(제공기관 안내).
- 함께 쓴 서비스: LLM 은 SSAFY GMS(OpenAI 호환), 지도는 키가 필요 없는 Google 지도 검색·임베드 주소(Tool 아님, 실행 흐름·화면이 직접 만듦).

### 2.2 Tool 결과를 제약과 비교해야 답할 수 있는 요청 (3개 이상)

| 요청 | 비교하는 제약 | Tool 결과 없이 LLM 만으로 답하면 틀리는 점 |
|---|---|---|
| "인천공항에 9시 도착하는데 탈 수 있는 오사카행" | 출발 ≥ 공항 도착 + 준비 시간(국제선 기본 120분) | 오늘 실제 운항·지연·결항을 모르니 없는 편이나 이미 결항된 편을 추천한다 |
| "김포에서 제주 가는 가장 빠른 편, 오후 3시 이후" | 출발 ≥ 15:00, 지금 이후, 결항 제외 | 시간표가 날마다 바뀌어 기억 속 편명·시각이 틀린다 |
| "빠른 시일 내에 센다이 가는 편" | 오늘 편이 없으면 다음 날로 넓힘 (재계획) | 직항이 있는 날을 모르고, 없는 날에 '있다'고 지어낸다 |
| "KE1205 탑승구 어디야?" | 오늘 실시간 탑승구·예상 시각 | 탑승구는 당일 배정 값이라 LLM 이 알 수 없다 |
| "인천공항 출국장 약국 어디 있어?" | 출국장(area=D)·키워드 | 매장 위치·운영 시간이 바뀌어 틀린 위치를 말한다 |

재계획이 의미 있는 이유: 시간 조건·날짜에 맞는 편이 0건인 경우가 흔하고(심야, 주 몇 회 운항 노선), 조건을 넓히면 대안이 나옵니다.

### 2.3 저장 · 조회 · 수정 · 삭제할 결과물

**출국 계획** — 제목, 메모, 출발 공항, 편명, 노선(국내/국제), 출발 날짜(`flight_date`), 출발 예정·예상 시각, 체크인 마감(추정), 준비 시간, 내 공항 도착 예정, 생성 일시(`created_at`).
같은 날짜에 공항 준비 시간대(도착 예정 ~ 출발)가 겹치는 계획이 있으면 **저장은 하되** 저장 결과의 `warnings` 로 겹치는 계획을 알립니다 (F3015).

### 2.4 판단이 위험한 도메인인지

건강·금융이 아닌 여행 일정 도메인이라 면책 안내는 두지 않습니다. 대신 운항 정보는 실시간으로 바뀌므로 운항 관련 답변마다 "출발 전에 항공사 안내를 다시 확인하십시오"를 붙입니다.

## 3. 서비스 시나리오 (명세 2.2)

### 3.1 요청 분류와 조건

요청은 출발 편 찾기 · 도착 편 · 편명 조회 · 혼잡/예상 승객 · 시설 · 계획 안내 · 인사·사용법 · 그 밖으로 나눕니다. 조건은 세 묶음으로 뽑고 말하지 않은 값은 비워 둡니다.

| 구분 | 필드 | 예 |
|---|---|---|
| 기준 조건 | 날짜, '빠른 시일 내', 이 시각 이후, 출발(기준) 공항, 편명 | 내일, 오후 3시 이후, 김포 |
| 선호 조건 | 목적지·출발지(도시·공항), 가장 빠른 편, 시설 종류 | 제주, 가장 빠른, 약국 |
| 제약 조건 | 이 시각 전까지, 공항 도착 시각, 준비 시간 | 7시 전, 공항에 1시 반 도착, 준비 1시간 |

### 3.2 대표 요청과 Tool 순서

| # | 요청 | Tool 순서 | 재계획 |
|---|---|---|---|
| S1 | 내일 인천공항에 9시 도착하는데 탈 수 있는 오사카행 | search_departures(ICN, 내일) → 승객 예고(보조) → 판단 → (상세 생략: 인천 목록에 탑승구 있음) | 없음 (한 번에 충족) |
| S2 | 김포에서 제주 가는 가장 빠른 편, 23시 59분 이후로 | search_departures(GMP→CJU, 2359~) → 혼잡도(보조) → 판단 0건 → **재계획**: 시간 조건 해제 → 판단 → get_flight_detail(고른 편명) | 1회 |
| S3 | 빠른 시일 내에 김포에서 센다이 가는 편 | search_departures(GMP→SDJ) → 0건 → 1일 뒤 → 2일 뒤 → 3일 뒤 | 3회 → **상한 도달**, 사유와 함께 응답 |
| S4 | 김포에서 제주 가는 가장 빠른 편 (보조 도구가 실패하는 상황) | search_departures → 혼잡도 **실패** 기록 → 판단 → 상세 → 응답 | 없음 (Tool 하나 실패) |
| S5 | 안녕! 뭘 할 수 있어? | Tool 없음 (계획 단계에서 도구 없이 바로 응답) | 없음 |
| S6 | (한 달 뒤) 12월 20일 김포에서 제주 | 자료 범위 밖 → 같은 요일 운항표로 조회, 답에 '추정' | 없음 |
| S7 | 가장 빠른 비행기 알려줘 | Tool 부르기 전에 **되묻기**: 출발 공항이나 목적지를 알려 달라 | 없음 |
| S8 | (S1 다음) 김해에서는? | 목적지·날짜는 이어받고 출발 공항만 바꿔 다시 조회 (F3010) | 상황에 따라 |

### 3.3 저장할 결과물과 겹침 처리

AI 답의 추천 카드에서 '이 편으로 계획 저장'을 누르면 계획 입력칸이 채워지고, 사용자가 내 공항 도착 예정을 넣어 저장합니다. 편명으로 출발 시각을 다시 조회해 **체크인 마감 = 항공기 출발 시간 − 공항 체크인 시간(분)** 을 계산합니다. 체크인 시간은 공항·항공사마다 달라 사용자가 넣은 값을 쓰고, 비워 두면 국내선 60분·국제선 120분을 기본값으로 씁니다. 도착 예정이 마감보다 늦으면 저장을 막고(422), 목록의 '여유'는 체크인 마감과 내 공항 도착 예정 사이의 분입니다. 같은 날 준비 시간대가 겹치는 계획은 저장은 하고 경고로 알립니다.

## 4. 기능 요구사항 (명세 2.6 · 3장)

필수 F3001 ~ F3019 는 모두 구현했고, 심화는 F3020 을 선택했습니다. 항목별 구현 위치는 [SPEC_CHECK.md](SPEC_CHECK.md), 실행 결과는 [VERIFICATION.md](VERIFICATION.md).

| 번호 | 분류 | 요구사항명 | 요구사항 상세 (항공 도메인) | 우선순위 | 상태 |
|---|---|---|---|---|---|
| F3001 | Tool | Tool 명세 정의 및 등록 | 도구 11개(외부 API 툴 9, 로컬 서버 API 툴 2)의 이름·설명(언제 쓰는지)·입력 스키마를 레지스트리에 등록하고, 성공·실패를 같은 봉투(ok/data, ok=false/error{code,message})로 돌려준다 | 필수 | 구현 |
| F3002 | Tool | 후보 조회 Tool | 출발·도착 시간표(인천은 인천국제공항공사, 14개 공항은 한국공항공사 — 서로 보충)로 후보 편을 확보한다. 날짜를 생략하면 오늘, 오늘은 지금 시각부터. 자료 범위(오늘 −3일 ~ +6일) 밖 날짜는 같은 요일 운항표로 조회하고 요청 날짜·조회 날짜·'추정'을 함께 밝힌다. 다음 Tool 입력이 될 편명·공항을 돌려준다 | 필수 | 구현 |
| F3003 | Tool | 상세정보 조회 Tool | 판단이 고른 편명으로 탑승구·터미널·상태·예상 시각을 조회한다. 출발 시각이 없는 편은 값을 채우지 않고 판단하지 않은 채 제외한다 | 필수 | 구현 |
| F3004 | Tool | 보조 정보 검색 Tool | 다른 출처의 외부 API 로 혼잡도·예상 승객·시설·매장을 찾고 이름·위치·운영 시간·지도 링크를 준다. 결과가 없으면 count 0 · empty · '결과 없음' note | 필수 | 구현 |
| F3005 | Agent | 사용자 요청 분석 | 날짜·시각·공항(기준), 목적지·가장 빠른 편(선호), 이 시각 전까지·공항 도착 시각·준비 시간(제약)을 뽑는다. 말하지 않은 조건은 비운다 | 필수 | 구현 |
| F3006 | Agent | 작업 계획 수립 | 의도별로 필요한 Tool 과 순서를 계획하고(state 에 보관), 인사·사용법처럼 도구가 필요 없는 요청은 도구 없이 답한다 | 필수 | 구현 |
| F3007 | Agent | Tool 호출 및 결과 통합 | 계획대로 호출하고 결과를 모은다. 고른 편명을 상세 조회 입력으로 넘기고, 도구가 실패해도 사유를 남기고 다음 단계로 간다 | 필수 | 구현 |
| F3008 | Agent | 제약 적합성 판단 | 공항 도착 + 준비 시간 = 기준 시각을 계산해 출발과 비교한다. 체크인 마감처럼 API 로 확인할 수 없는 값은 출발 시각에서 역산하고 '추정'으로 표시한다 | 필수 | 구현 |
| F3009 | Agent | 재계획 | 후보가 0건일 때만 시간 조건 해제 → 다음 날 순으로 넓혀 재계획(상한 3회). 받은 결과는 재사용하고, 상한에 닿으면 사유와 함께 멈춘다 | 필수 | 구현 |
| F3010 | Agent | 대화 맥락 유지 | 직전 의도·조건을 세션별로 저장하고, 후속 요청에서 바꾼 조건만 갱신한다. Tool 원본 응답은 보관하지 않는다 | 필수 | 구현 |
| F3011 | Agent | 최종 응답 생성 | 추천 편·늦어도 공항 도착·체크인 마감(추정)·보조 정보·판단 기준·제외한 후보와 사유·가정·근거 자료를 함께 답한다 | 필수 | 구현 |
| F3012 | 로깅 | 실행 이벤트 발행 | 단계 진입·종료, Tool 호출·결과·소요 시간, LLM 의 의도 판단과 이유를 세션 번호와 함께 발행한다. 발행은 구독자와 무관하다 | 필수 | 구현 |
| F3013 | 로깅 | 로깅 Agent 수집·저장 | 이벤트를 구독해 세션 단위로 발생 순서대로 SQLite 에 원본 그대로 저장한다. LLM 을 쓰지 않고, 저장 실패에도 대화는 계속된다 | 필수 | 구현 |

## 6. 기획 검증 결과 (명세 2.7)

자동 기록: `python verify/run_checks.py` 를 실행하면 아래 1~3 을 다시 실행해 [verification/PLANNING_CHECK.md](verification/PLANNING_CHECK.md) 에 남깁니다 (외부 API 호출 출력, LLM 연결·Tool 선택, 대표 요청 단계별 추적).

### 6.1 도메인 조건 확인 — 외부 API 호출

`api_check/check_apis.py` 로 서비스마다 한 번씩 실제 호출해 응답을 받았고(개발 중 기록), 그 결과로 설계를 아래처럼 바꿨습니다. 최신 호출 결과는 검증을 돌릴 때마다 [verification/api_check.txt](verification/api_check.txt) 에 다시 남습니다.

| 확인한 것 | 결과 (개발 중 기록) | 설계에 반영 |
|---|---|---|
| 인천 여객기 운항 현황 상세 | 호출 성공. 응답의 `items` 가 목록으로 바로 오는 형식 | 공통 파서가 두 형식(`items.item`, `items[]`)을 모두 읽게 함 |
| 한국공항공사 실시간 운항 | 호출 성공. `numOfRows=500` 이면 제공기관 코드 04 | 한 페이지 100건으로 나눠 받고, 첫 페이지가 04 면 50건으로 다시 시도 |
| 한국공항공사 상업시설 임대계약(airport-retail-contract) | 승인 뒤에도 코드 04, 공항 구분 없음 | **전국공항 임대계약 정보(airport-lease-contract)로 교체** (공항 코드로 거를 수 있음) |
| 한국공항공사 시간대별 탑승승객 수(daily-expect-passenger) | 기본 주소에서 코드 12(서비스 없음) | /info, /list 를 차례로 시험하고, 모두 안 되면 실시간 운항 편수로 대신 (`fallback_reason` 에 밝힘) |
| 인천 상업시설 정보(StatusOfFacility) | 2일차 이후 찾음, 호출 성공 | 인천 시설 도구 추가 (기획 때는 '인천 면세장 위치 API 없음'으로 봤음) |
| 키를 비운 상태 | 포털 호출이 인증 오류로 끝남 | 키가 없으면 호출하지 않고 `NO_KEY` 로 돌려주고, 재계획 없이 설정 안내 |

서로 다른 정보를 주는 외부 API 3종 이상(운항·혼잡·승객 예고·시설·매장)을 호출해 도메인 조건을 충족했습니다.

### 6.2 Tool 설계 확인 — 실제 응답과 출력 구조 대조

| 대조한 것 | 발견 | 처리 |
|---|---|---|
| 인천 예상 시각 필드 | 명세 표는 `estimatedDatetime`, 샘플은 `estimatedDateTime` (대소문자 다름) | 필드 이름을 대소문자 무시로 읽음 (`common.pick`) |
| 한국공항공사 도착 공항 코드 | 문서 표기 `arrvAirportCode` 와 다른 이름(`arrAirportCode`)이 올 수 있음 | 두 이름 모두 읽음 |
| 한국공항공사 목록의 탑승구 | 없음 | 당일 편은 실시간 info 로 상세 조회(`get_flight_detail`), 다른 날은 '탑승구 미배정' 표시 |
| 제약 판단에 필요한 값(출발 시각) | 대부분 있으나 비는 줄이 있음 | 비면 판단하지 않고 제외(사유 기록) |
| 결과가 없을 때 | 운항 0건은 정상 응답 | 실패가 아니라 `count: 0` + note, 시설은 `empty` + '결과 없음' |
| 호출 한도 | 인천 승객 예고 1,000건/일 등 | 5분 캐시(시설 6시간) |

### 6.3 도구 연결 확인 — LLM

- SSAFY GMS 로 한 번 호출해 응답을 받습니다 (`.env` 의 `GMS_API_KEY`, 접속 주소 `https://gms.ssafy.io/gmsapi/api.openai.com/v1`).
- Tool 명세(이름·설명·입력 스키마)를 함께 넘겼을 때 LLM 이 요청에 맞는 Tool 을 고르는지 확인합니다 (예: "김포에서 제주 가는 가장 빠른 편" → `search_departures`, "안녕" → Tool 없음). 결과는 PLANNING_CHECK.md 2장.
- 설계 결정: 실제 서비스에서는 LLM 이 문장을 **의도 + 조건으로 구조화하는 데만** 쓰이고, 도구 선택·순서·판단은 규칙으로 합니다. 같은 요청에 늘 같은 계획이 나오고, 계산 값을 지어내지 않게 하기 위해서입니다. 키가 없거나 실패하면 규칙 기반 분석으로 넘어가고 그 사실을 답과 실행 로그에 남깁니다.

### 6.4 설계 시험과 설계 변경

대표 요청 S1("내일 인천공항에 9시 도착하는데 탈 수 있는 오사카행")을 설계한 단계대로 따라가며 각 Tool 의 입력이 앞 단계 결과로 채워지는지 확인했습니다: 분석(기준 `{date: 내일, airport: ICN}` · 선호 `{destination: 오사카}` · 제약 `{arrive_airport_at: 0900}`) → 계획(`search_departures{airport: ICN, date: 내일}`, 보조 `get_incheon_passenger_forecast{selectdate: 1}`) → 판단(09:00 + 120분 = 11:00 이후 출발만 후보, 이른 편은 '준비 시간 부족'으로 제외) → 응답. 재계획 요청 S2 · S3 로 재계획 조건과 상한이 설계대로 동작하는지도 확인했습니다.

| 기획(2일차) | 시험 결과 | 바꾼 설계 |
|---|---|---|
| 준비 시간을 말하지 않으면 되묻기 | 대표 요청 대부분에 준비 시간이 없어 한 번에 답하지 못함 | 국내선 60분·국제선 120분 기본값을 쓰고, 답에 '기본값으로 계산'을 밝힘 |
| 범위 밖 날짜는 가장 가까운 허용일로 조정 | 요일이 달라져 주 몇 회 운항 노선이 틀어짐 | **같은 요일**인 날의 운항표로 조회하고 '추정'을 밝힘 |
| 필수 Tool 5종 | 편명 조회, 시간대별 흐름, 시설, 공항 검색이 필요 | 외부 API 툴 9 + 로컬 서버 API 툴 2 = 11종 |
| 한국공항공사 상세는 depart + f_id | 편명 필터가 없고 탑승구도 없음 | 실시간 info(탑승구 포함)로 상세 조회 |
| 상업시설은 지사 → 공항 매핑표 | 서비스 자체가 04 로 실패 | 공항 코드가 있는 임대계약 정보로 교체, 매핑표 불필요 |
| 재계획: 날짜 +1 → 시간창 확대 | 시간 조건이 있으면 같은 날 전체가 더 가까운 대안 | 시간 조건 해제 → 1·2·3일 뒤 순서 (상한 3회) |
| 체크인 마감을 기준으로 판단 | 항공사마다 달라 공공데이터에 없음 | 판단은 준비 시간 기준, 체크인 마감은 '(추정)'으로만 표시 |
